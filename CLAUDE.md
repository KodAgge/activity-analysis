```bash
uv sync                                  # create .venv and install
```

This checkout's `.envrc` exports `ACTIVITY_ANALYSIS_HOME` as the checkout, so the store is `./data`; without direnv, pass `--root .`.

## What this is

A local training analysis application for running.
The differentiator over Strava and Garmin is not the overview or the activity browser, which both do well.
It is the trend analysis: normalising metrics so that genuine fitness change is separable from variation in pace and terrain.

Concretely, the metrics that justify the project are cadence at a fixed reference pace, heart rate at a fixed reference pace, aerobic decoupling, and race predictions from extracted best efforts.
Plotting raw cadence or raw average heart rate over time is what the incumbents already do, and it mostly measures how fast the athlete happened to run that day.

## Stack

Python 3.12 managed with `uv`.
FastAPI, pandas, DuckDB querying canonical Parquet, `fitdecode` for FIT parsing, `typer` for the CLI, `shapely` for the territory geometry.
React and TypeScript via Vite for the frontend, with uPlot for the time-series charts and plain SVG where a chart needs per-point hit testing, TanStack Query and Router, and API types generated by `openapi-typescript`.
MapLibre GL, `pmtiles` and `@protomaps/basemaps` render the route hero's basemap; `docs/reference/frontend.md` has how it is fetched, served and drawn.
The `pmtiles` CLI, 1.31.2, is an external binary `activity-analysis tiles` needs on `PATH`, installed outside `uv` and `npm`.
`ruff` for lint and format, `mypy` for types, `pytest` for tests.

One binary data file is committed: `src/activity_analysis/data/places.parquet`, a 3.5 MB GeoNames extract that resolves an activity's start position to a place name entirely offline.
`scripts/build_places.py` records its provenance, its CC BY 4.0 licence and the measurements behind it.

The maintainer is strongest in Python.

## Architecture

Layered pipeline, each layer independently testable and rebuildable:

```
data/raw/          unpacked export archives (gitignored)
   -> ingest/      discover -> fit_reader | gpx_reader -> normalize -> dedupe
data/canonical/    activities.parquet, laps.parquet, streams/<activity_id>.parquet,
                   profile_observations.parquet, device_vo2max.parquet
   -> analysis/    resample(1 Hz) -> best_efforts -> efficiency fits -> predictions
data/derived/      streams_1hz/, activity_metrics.parquet, best_efforts.parquet,
                   activity_tags.parquet, zone_time.parquet, athlete_profile.parquet,
                   activity_efficiency.parquet, athlete_fit.parquet, fitness_series.parquet,
                   routes.parquet, route_runs.parquet, territory_claims.parquet,
                   territory_regions.parquet, territory_parts.parquet,
                   sport_reclassifications.parquet
   -> store/db.py  DuckDB views over both layers
   -> api/         FastAPI, JSON
   -> web/         React + TypeScript

data/basemap/      manifest.json, areas/<id>.pmtiles, assets/ (fetched by tiles, gitignored)
   -> api/         read as files, not through DuckDB
```

The point of the split is that a metric bugfix means rerunning `recompute`, not reparsing several thousand FIT files.
Do not collapse these layers or add compute-on-read shortcuts in the API.
That was considered and rejected: a metric computed on read is computed again on every request and can disagree with the same metric in the stored layer.

## Domain constraints that are easy to get wrong

These cost real debugging time if violated, and several are not discoverable from the code alone.

**There is no Strava API.**
The endpoints needed for stream data require a paid subscription the maintainer does not have.
Data arrives only as bulk export archives.

**FIT is the primary format, GPX is a degraded fallback.**
This was decided from measurement, not preference.
For the same activity, GPX carries 10.2x the sample-to-sample speed noise, because speed must be derived from GPS coordinates rather than read from the device.
GPX also has no laps, no HR zones and no athlete profile.
Both headline metrics divide by speed, so that noise propagates straight into them.
Activities ingested via GPX are flagged so trend analyses can exclude them.

**All canonical data is SI.**
Metres, seconds, m/s, bpm, spm.
Pace in min/km, local timezones and any imperial display are presentation concerns handled at the API boundary or in the frontend.
Never store pace.

**Unit conversions applied once, at ingestion:**
- Coordinates are semicircles in FIT: `degrees = semicircles * 180 / 2^31`.
- Cadence is rpm for one foot: `cadence_spm = (cadence + fractional_cadence) * 2`.
- Prefer `enhanced_speed` over `speed` and `enhanced_altitude` over `altitude`; the enhanced fields have greater range at the same resolution, and the Venu 2 Plus writes no legacy `speed` field at all.
- Local time is an offset, not a timestamp: `utc_offset_s = activity.local_timestamp - activity.timestamp`, compared as naive wall clocks because fitdecode mislabels the local one as UTC. Null for GPX, which records no offset. A UTC instant alone cannot say what time of day a run happened: 15 of 324 runs were recorded outside the athlete's usual offsets, and reading them in the home timezone puts all 15 at the wrong hour. See "The contract" in `docs/reference/api.md`.

**`athlete_profile` is time-versioned, and this is not optional.**
Max HR, resting HR and body mass drift over years.
Applying today's max HR to a run from three years ago silently corrupts every zone distribution and every normalised trend.
These are device settings rather than measurements, though: they change only when the athlete edits them, so expect few rows and long static stretches.
A profile that has been constant for a year means nobody touched the setting, not that the athlete did not change.
Version the table, but do not read anything physiological into the shape of its history.

**Records are irregularly sampled at 1 to 9 second intervals.**
All rolling-window analysis runs on the resampled 1 Hz derived grid, never on raw records.
A gap over 15 s across which the implied speed is under 0.5 m/s is a stop, and one over 120 s that is not a stop is an outage: stopped seconds leave moving time, outage seconds stay in it, neither reaches time in zone because heart rate is null across both, and the grid flags each with `paused` and `outage`.
**The grid never holds distance across either.**
Distance and position interpolate across every gap and only the sensor channels are nulled, because the odometer is the record of what happened.
Holding was tried and it manufactured 400 m best efforts of 0.89 s and of 88 s at 4.5 m/s, unflagged, by dumping a whole gap's advance into the second the recording resumed.

**`zones_target` in FIT is per sport, not per athlete.**
Maximum heart rate is 207 for running and 205 for walking in this export, so the athlete profile is versioned from running observations alone.
Versioning every sport together turned five real intervals into 297 spurious ones.

**Best efforts are elapsed time and span pauses.**
5 km, five minutes standing still, then 5 km is a 65:00 ten kilometre. Moving time would say 60:00, which is the one rule under which resting is free.

`docs/reference/derived-layer.md` has the full derived layer reference: pause constants, column meanings, zone conventions and the profile tables.
Read it before touching `src/activity_analysis/analysis/`.

`docs/reference/api.md` has the API reference: the endpoints, the units and time contract, the connection model and the traps.
Read it before touching `src/activity_analysis/api/`.

`docs/reference/frontend.md` has the frontend reference: the views, where the arithmetic lives, the token and type-generation contracts and the traps.
Read it before touching `web/`.

**Activity identity is content-derived, in two stages**, never a source ID.
Provisional identity is `hash(athlete_id, start time floored to the minute)`.
Before writing, a candidate is reconciled against stored activities for the same athlete: start within 90 s and, when both are known, distance within 2%; a match adopts the stored id.
Source priority Garmin FIT > Strava FIT > GPX then decides which copy survives.

Do not go back to hashing measured quantities into the identity.
That was tried and it failed on these very fixtures: the FIT reports 7456.06 m and the same run's GPX yields 7454.85 m, which straddles a 10 m bucket edge and splits one run into two activities.

**Ingestion is idempotent** via a SHA-256 content hash per source file.
Re-dropping an archive must be a no-op.

**`fitdecode` returns the raw integer for an enum value it cannot name.**
`sport`, `sub_sport` and `lap_trigger` therefore arrive as `str` or `int` depending on the activity, and a real export is full of the latter.
`normalize` coerces them to text so the canonical string columns hold the unnamed value rather than dropping it.

**`fitdecode` can yield one field name twice in a message.**
A Garmin-original FIT carries `enhanced_avg_speed` and `enhanced_max_speed` in every lap and session, then an empty copy expanded from the invalid legacy `avg_speed` and `max_speed`.
`fit_reader.field_values` keeps a value over a later empty copy; reading fields last-wins emptied every Garmin lap's speed until `INGEST_VERSION` 3.

**`fitdecode` does not decompress `.fit.gz`.**
Passing a gzipped path directly raises `FitHeaderError: not a FIT file @ 0`.
Wrap it in `gzip.open()` and hand `fitdecode.FitReader` the file object.
Strava's bulk export ships gzipped, so this is the normal path, not an edge case.

## Test fixtures

`data/examples/` holds five real Garmin Venu 2 Plus running activities, one of which is also present as a Strava-exported GPX and so serves as the cross-format and deduplication fixture.

**Filenames and activity names are not identifiers.**
Strava names a file downloaded on its own after the activity, and its default Swedish names collide freely.
Never key ingestion logic on filename or activity name.

**Analysis correctness is tested against synthetic fixtures with known analytic answers, not against real data.**
Real noisy data has no independent ground truth, so a test against it proves nothing beyond "the code ran".
Use the real files for ingestion and parsing tests, synthetic data for maths.
The single exception is the device's own `time_in_zone` totals, the one place in this project where a derived metric has real ground truth on real data, so `tests/test_zones.py` asserts against them.

`docs/reference/test-fixtures.md` has the fixture inventory, the golden values for the 2026-08-28 reference activity, and the device's field coverage.
Read it before writing ingestion or parsing tests.

`docs/reference/demo-store.md` covers `scripts/build_demo_store.py`, three years of synthetic runs re-timed from the fixtures, which the README screenshots are taken from and which holds a 12 hour run for checking performance at ultra length.

`docs/reference/releasing.md` has how a release is built and published: a GitHub release carrying the wheel, which the setup scripts and the README install from.

## Documentation and planning

- `docs/reference/` - living reference material. Detail needed only for one kind of task, kept out of this file.
- `docs/reference/math/` - the derivations behind every computed metric. Start at its `README.md`, which maps the whole pipeline.

The maintainer's design documents, implementation plans and backlog are kept out of this repository, under the gitignored `docs/specs/`, `docs/plans/` and `docs/BACKLOG.md`; `CLAUDE.local.md` says where they live when this machine has them.
No public file points at them.
What a reader of this repository needs from a decision belongs in a reference document.

**The repository is public, so docs, comments and tests quote real data only in relative terms.**
Figures from the committed fixtures may be quoted freely.
From a real export, quote only sample sizes, proportions and relative errors, such as "15 of 324 runs" or "within 3% of the realised time".
Never quote absolute performances, body metrics, place names, positions, dates of personal events or real activity ids.
`scripts/privacy_scan.py` checks the tree against a denylist kept out of the repository, since the list is itself personal data.

**Any module that computes a metric gets a document under `docs/reference/math/`, and a phase is not complete until it exists.**
What such a document must contain is owned by "Conventions for documents in this directory" in `docs/reference/math/README.md`.
This repo is meant to be readable by someone learning the domain, not only runnable.

**Keep this file short.**
It is read in full at the start of every session.
Anything that only matters for one kind of task belongs in `docs/reference/` behind a one-line pointer, not inline here.
